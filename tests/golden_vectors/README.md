# Golden Vectors

`vectors.json` records what the contract headers put on the wire, as
generated by the headers themselves. It is the oracle the Python codec in
`bindings/python` is tested against, and the file a future re-declaration
of the payload layouts (#18) must reproduce byte for byte.

## Contents

- `constants`: every numeric `#define` the codec exports, with its value.
- `encode`: one record per call of a `*_send_*` or `*_query_*` helper: the
  arguments, the type id and opcode of the frame it wrote (with the macro
  names), and the payload bytes as lowercase hex. Query helpers write a
  `CRUMBS_CMD_SET_REPLY` frame whose payload names the requested opcode.
- `parse`: one record per call of a payload parser on a known reply: the
  payload, the C return code, and the parsed fields (`null` when the parser
  rejected the payload, which the short-payload records exercise).

## Regenerating

`gen_vectors.c` builds as `bread_contracts_gen_vectors` with the test
targets (`BREAD_CONTRACTS_BUILD_TESTS`, on by default at top level):

```bash
cmake -S . -B build/contracts -DCMAKE_PREFIX_PATH="<linux-wire-install>;<crumbs-install>"
cmake --build build/contracts --target bread_contracts_gen_vectors
./build/contracts/bread_contracts_gen_vectors tests/golden_vectors/vectors.json
```

CI runs exactly this and fails on `git diff --exit-code`, so a header change
that moves bytes must be committed together with the regenerated file.
The output is deterministic: fixed key order, no timestamps.

## Adding a vector

Add a call in `emit_encode_vectors()` or `emit_parse_vectors()`, regenerate,
and commit the diff. The Python tests fail on a header opcode with no vector
and on a Python encoder or parser with no vector, so a new op needs both the
C call here and the Python function.
